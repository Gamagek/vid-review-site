## Implemented behavior

- New first-party `tiktok-oembed-cache.js` shares one pending lookup per canonical video through the parent page. Isolated player documents use that broker; standalone documents retain their own broker fallback. The actual request is still a direct browser fetch from the isolated document, with the owner's real viewer identity and the exact `/api/watch?url=...` path. No server proxy or general-site CSP origin is added.
- Validated successful **public metadata** is reused in memory and session storage for 30 minutes. Close/reopen and normal same-tab document reloads reuse that successful record. With storage disabled, same-page memory reuse still works. Expired entries require a new deliberate lookup; pending coalescing is per page, not a cross-tab lock or a guarantee across an interrupted full-page reload.
- Store only exact source ID/creator, bounded public caption/author text, a dated remaining-request value and expiry. No raw API HTML, signed poster URL, TikTok iframe response, video/audio bytes, credentials or new D1/R2 cache is stored. The counter is labelled **at the last lookup**, not presented as a freshly queried quota on replay.
- A known owner-API 429 takes precedence over a prior successful cache entry. Honor accessible Retry-After seconds/date; default to a 60-second local pause when absent/inaccessible. Other failures have a finite Retry-After/default pause too. A 12-second abort and 64 KiB JSON cap remain. There is no stats polling, automatic retry, quota replacement or alternate provider route.
- Repeated Play calls while this same source's dialog is open retain its one iframe/listener/readiness timer. Duplicate service/client script execution is guarded. Closing/background cleanup still destroys the official player to stop media; no undocumented pause/render API is introduced.
- Each deliberate reopen still needs a clean official `embed.js`/TikTok iframe lifecycle. This reduces owner-API metadata requests; it **does not cache or eliminate TikTok's video/player requests**, read cross-origin error bodies in production, or promise removal of its overload/429 restriction. Player text now acknowledges possible unavailability and does not encourage repeated close/reopen attempts.
